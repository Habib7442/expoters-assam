## Summary

Spec 0004's migration of product/company image storage from Supabase Storage to Cloudflare R2. The code itself is clean and well-shaped: the two-file split (`r2-client.ts` unguarded core taking explicit credentials, `r2.ts` `server-only` entry point reading env once and failing fast) is the right answer to the "plain script can't import a `server-only` module" problem, and it preserves the browser/server boundary AGENTS.md §9 demands, no secret reaches client code. Upload key derivation is entirely server-side, so there is no path-traversal or cross-user-overwrite surface. The headline concern is not in the new module but in what the migration leaves behind: the change simultaneously revokes public read on both Supabase buckets *and* deletes the Supabase host from `next.config.ts`'s `remotePatterns`, with no audit, backfill, or defensive guard for any `companies.logo_url` / `products.image_url` value still pointing there, and `next/image` throws at render rather than degrading to a broken image. Two smaller contract gaps in `parseR2Url` and one misleading line in the spec's own deployment checklist round out the list.

Checks re-run independently for this review: `npx vitest run` → 9 files, 48 tests passed; `npx tsc --noEmit` → clean; `npx eslint` → clean.

## Major

### 🟠 Nothing audits, backfills, or guards image URLs left pointing at the now-closed Supabase buckets, `supabase/migrations/20260909020000_disable_supabase_storage_public_buckets.sql:10`, `next.config.ts:17`, `components/exporter-card.tsx:18`

**Problem**: This change makes two irreversible-in-effect moves at once, `update storage.buckets set public = false` on `product-images`/`company-logos`, and removal of `wpoikxdhzpzubionhkcw.supabase.co` from `images.remotePatterns`. The only row it repairs is the demo product's, via `scripts/seed-demo.ts:145`. Nothing checks whether any `companies.logo_url` still holds a `…supabase.co/storage/v1/object/public/company-logos/…` URL. Spec 0005's logo upload flow shipped in commit `41b2ae3` against that bucket and was live from 2026-09-03 until today, so such a row is possible; I could not confirm the row count (a live DB read was not available to me in this session), which is exactly why it should be confirmed rather than assumed.

**Why it matters**: The failure mode is worse than a broken image. `next/image`'s default loader throws `Invalid src prop … hostname is not configured` (`node_modules/next/dist/shared/lib/image-loader.js:101`) whenever the src host has no matching remote pattern, and that guard runs for any `NODE_ENV !== 'test'` on the Node runtime, not dev only. `ExporterCard` renders `logoUrl` in the home page's Featured Exporters (`app/page.tsx:257`) and `app/products/[slug]/page.tsx:96` renders the company logo, so one stale row throws during render of a public page, not a missing thumbnail. The same risk is open-ended going forward: spec 0004's own Follow-up notes the separate admin app has not been told about R2 yet, and that is the app where images actually get added, so an admin writing a Supabase Storage URL by habit takes the public home page down.

**Suggested fix**: Two parts. (1) Before merge, run one query against `companies.logo_url`, `products.image_url`, and `products.gallery_urls` for any value containing `supabase.co/storage`; if any exist, add a migration that nulls or rewrites them (a null logo already renders a fallback in `ExporterCard`), and record the result in `verify.md` next to the AC-6 evidence. (2) Regardless of the count, make the render path non-fatal: have the card/product components treat a non-R2 host as "no logo" (or centralize that check next to `parseR2Url`, which already knows the domain shape), so a bad row degrades instead of throwing. Also worth pulling the admin-app notification out of Follow-up and doing it as part of this merge, since it is the most likely source of a future bad row.

## Minor

### 🟡 `parseR2Url` throws `URIError` on a malformed percent-escape, contradicting its documented "never throws" contract, `lib/storage/r2-client.ts:98`

**Problem**: `keyParts.map(decodeURIComponent)` throws on an invalid escape sequence. Confirmed by direct execution: `parseR2Url("images.exportersasssm.com", "https://images.exportersasssm.com/logos/100%.webp")` throws `URIError: URI malformed`. Spec 0004's API-surface table states this function "never throws, returns `null` on a non matching URL", and `lib/storage/r2-client.test.ts:118` ("never throws on a malformed URL") does not actually exercise it, its input `"not a url"` returns `null` at the prefix check on line 90 and never reaches a `decodeURIComponent` call.

**Why it matters**: The only current call site wraps it in `try/catch` (`lib/actions/business-listing.ts:88`), so today the blast radius is one silently skipped delete. But the stated contract is what the next caller will rely on, including the separate admin app that spec 0004 expects to adopt this module verbatim, and there the throw would surface as an unhandled error rather than a `null`.

**Suggested fix**: Wrap the decode (both the category and the key segments) so a decode failure returns `null`, matching the documented contract, and point the existing "never throws" test at an input that actually reaches the decode.

### 🟡 `parseR2Url` returns an empty key for a trailing-slash URL, `lib/storage/r2-client.ts:93`

**Problem**: `if (keyParts.length === 0) return null` only rejects a URL with no slash after the category. `https://images.exportersasssm.com/products/` splits to `["products", ""]`, so `keyParts.length === 1` and the function returns `{ category: "products", key: "" }` (verified by execution). `deleteFromR2` would then issue a `DeleteObject` for the bare key `products/`. The test on line 114 covers only the no-trailing-slash variant, so the gap is invisible.

**Why it matters**: Harmless against R2 today (a delete of a nonexistent key succeeds silently), but it is a "return null" case leaking through as a valid parse, and any future caller that trusts a non-null result to name a real object will act on garbage.

**Suggested fix**: Reject an empty key alongside the empty `keyParts` case, and add the trailing-slash input to the existing null-returning test block.

### 🟡 The spec's deployment checklist under-counts the env vars Vercel needs, `docs/specs/0004-cloudflare-r2-image-storage/index.md:88`

**Problem**: "No new Vercel-only configuration beyond adding the four secret vars to the project's env settings; the domain literal in `next.config.ts` needs no separate Vercel config since it ships in the built code." Five vars are required, and `R2_PUBLIC_IMAGE_DOMAIN` is one of them: `lib/storage/r2.ts:20` calls `requireEnv("R2_PUBLIC_IMAGE_DOMAIN")` at import time to build the returned public URL. The `next.config.ts` literal is a separate concern and does not substitute for it.

**Why it matters**: This bullet is the deployment checklist for a repo with no `.env.example` and no env documentation in the README, so it is the only place a deployer finds this list. Following it literally sets four vars and the Vercel build fails at page-data collection for `/list-business`. The failure is loud rather than silent (which is why this is Minor, not Major), but it is an avoidable failed deploy.

**Suggested fix**: State all five vars explicitly and note that `R2_PUBLIC_IMAGE_DOMAIN` is needed both as a runtime env var (for `r2.ts`) and as the literal in `next.config.ts`, kept in sync by hand.

### 🟡 The seed script's new update-on-existing branch (AC-4) has no automated coverage, `scripts/seed-demo.ts:145-155`

**Problem**: `upsertProduct` changed from an early return to an update of `image_url`/`gallery_urls`, and this is the code that satisfies AC-4. With `TESTS = configured` (vitest), it is the one piece of changed branching logic in this diff with no test. `verify.md:23` records a live re-run, which is real evidence but not a regression guard.

**Why it matters**: A regression here is quiet: the seed reports success while the product page keeps rendering a stale URL, which is precisely the bug this branch was added to fix.

**Suggested fix**: Either add a small test with a faked Supabase client asserting the update fires with the new URL on the existing-row path, or, if mocking a script's Supabase client is judged not worth it, note explicitly in `verify.md` that AC-4 is live-verified only and has no regression guard.

## Strengths

- The `r2-client.ts` / `r2.ts` split is the right call and is executed cleanly: the unguarded core takes credentials as arguments and holds no ambient `process.env` reference, so splitting off the `server-only` guard does not weaken it. It mirrors the established `lib/supabase/admin.ts` precedent, and the reason is documented in both files rather than left as tribal knowledge.
- The logo object key is entirely server-derived, `auth()`'s `userId` + `crypto.randomUUID()` + an extension from a fixed MIME map (`lib/actions/business-listing.ts:79-84`). No user-supplied filename reaches the key, so path traversal and cross-user overwrite are both structurally impossible, not merely validated away.
- Per-segment `encodeURIComponent` with an exact `parseR2Url` inverse, and a test that genuinely round-trips a multi-segment key containing spaces (`lib/storage/r2-client.test.ts:99`). The spec records that this was a real bug caught and fixed, not a hypothetical.
- The env fail-fast in `r2.ts` is tested per-variable with `vi.resetModules()` and an import-time rejection assertion (`lib/storage/r2.test.ts:54`), which tests actual module-load behavior rather than asserting on a mock.
- The documentation trail is unusually honest: the AC-6 correction (RLS policy ≠ `storage.buckets.public`) is recorded in the migration, the spec, and the scope, and spec 0005's build-plan item 9 was revised *downward* to admit partial verification rather than left ticked. That is the kind of correction that normally gets quietly skipped.
- `next.config.ts:13-17` hardcodes the hostname with the reasoning inline, and `next.config.test.ts` locks it. Small, but it closes a class of build-vs-runtime env bug that is painful to diagnose in production.

## Test coverage

Good for the new storage layer, and mostly testing behavior rather than mocks. `r2-client.test.ts` drives the real functions against a fake `S3Client.send`, asserting the actual `PutObjectCommand`/`DeleteObjectCommand` input (bucket, prefixed key, body, content type, `Cache-Control`) plus the AC-5 checksum flags read back off a genuinely constructed client, that is the right seam. `r2.test.ts` mocks the core, which is correct there since the unit under test is the env-reading/wiring layer, and it verifies the fail-fast for each of the five vars. `business-listing.test.ts` covers the migrated call site's category/key shape, the upload-failure guard (RPC never called), and all three delete-on-replace branches including the swallowed-failure path.

Gaps, in rough priority order: (1) `scripts/seed-demo.ts`'s AC-4 update branch is untested (raised as Minor above); (2) `r2-client.test.ts:118`'s "never throws" test does not reach the code that can throw, and the trailing-slash parse is unasserted (both raised above), so the two `parseR2Url` defects sit in a blind spot the suite appears to cover; (3) `business-listing.test.ts:87` destructures only `[category, key]`, so nothing asserts the logo is passed as a `Buffer` with the file's own MIME type as `contentType`, worth one extra `toHaveBeenCalledWith` since `Buffer.from(await file.arrayBuffer())` is new code in this diff. Nothing in the suite covers the stale-Supabase-URL render path from the Major finding, which is expected (it is a data condition, not a unit), and is part of why a defensive host check at the render site would be worth having.
