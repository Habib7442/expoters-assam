# Review, master, 2026-08-27

**Reviewed by**: claude-opus-5 (author model not recorded; review run on a fresh model that did not write the code)
**Scope**: 17 files, uncommitted — scope feature 2 only ("database schema & access model", spec `docs/specs/0001-database-schema-access-model/index.md`)
**Verdict**: Blocked

## Summary

This change lands the whole data layer for spec 0001: three migrations creating the seven core tables, the two public views, every constraint/trigger/index, RLS plus the anon read policies and the storage buckets; five small TypeScript modules (`supabase`/`supabaseAdmin` clients, `assertOwnsCompany`, the `company_tiers` query helpers, `getOrCreateBuyerByPhone`); generated database types; and a 19-test vitest suite with its config. The SQL is the strongest part of the change — the `enquiries` `BEFORE INSERT` trigger (rather than a `CHECK`) and the `get_or_create_buyer` DB function are both non-obvious and both correct, and the author clearly ran `supabase db advisors` and acted on the findings.

The blocker is not in the design: two of the new test files fail TypeScript, and because `tsconfig.json` includes `**/*.ts` with no test exclusion, `npm run build` fails outright — a Vercel deploy of this tree would not ship. Beyond that, one security comment in the migration promises a protection that Supabase's default privileges do not actually give, and the phone normalizer hard-fails on two very common Indian input formats, which in this product means a silently lost lead.

## Blockers

### 🔴 `next build` and `tsc --noEmit` both fail on the new test files, `lib/supabase/admin.test.ts:6`, `lib/supabase/client.test.ts:6`

Line 6 then calls `createClientMock(...args)` with `args: unknown[]`, and line 30 destructures `createClientMock.mock.calls[0]!` as a 2-tuple. ```

```
lib/supabase/admin.test.ts(30,12): error TS2493: Tuple type '[]' of length '0' has no element at index '0'.
lib/supabase/admin.test.ts(30,17): error TS2493: Tuple type '[]' of length '0' has no element at index '1'.
lib/supabase/client.test.ts(6,58):  error TS2556: ...
lib/supabase/client.test.ts(30,12): error TS2493: ...
lib/supabase/client.test.ts(30,17): error TS2493: ...
```

`npx tsc --noEmit` → exit 1. `npx next build` → `Failed to type check.`, exit 1. (`npm test` and `npm run lint` both pass — vitest does not typecheck, and eslint does not run `tsc`, so the suite going green hides this.)

**Why it matters**: `AGENTS.md` Section 10 names `tsc --noEmit` and `npm run build` as required checks, and this change touches server modules, so `build` applies. **Suggested fix**: Give the mock implementation an explicit rest parameter so its call signature accepts the spread and its recorded calls are typed — e.g. declare it as a `vi.fn` whose implementation takes `(...args: unknown[])`, or annotate the mock's generic signature. Note that `assert-company-owner.test.ts` already avoids this by leaving `vi.fn()` implementation-free; the same shape would work here. Do **not** fix it by excluding `*.test.ts` from `tsconfig.json` — that would silently drop the whole suite out of the typecheck the project relies on.

## Major

### 🟠 The explicit revoke does not protect future tables, contrary to its own comment, `supabase/migrations/20260827065400_create_core_schema.sql:284`

**Problem**: The comment reads "Explicit revoke so a future table added without remembering RLS does not silently become a public write credential", and the spec repeats this in `## Feature design`. But `revoke insert, update, delete on all tables in schema public from anon, authenticated` applies only to the tables that exist at the moment it runs. Supabase's project bootstrap includes `alter default privileges ... in schema public grant all on tables to anon, authenticated, service_role`, so any table created by a *later* migration is granted `INSERT`/`UPDATE`/`DELETE` to `anon` all over again. The stated defense-in-depth simply is not in place for the case it names.

**Why it matters**: The claim is load-bearing — a future contributor reading this comment will reasonably believe forgetting `enable row level security` on a new table is survivable. It isn't: a new table without RLS would be an anon-writable table on a public REST endpoint. (AC-2 for the *current* seven tables is genuinely satisfied — `verify.md` confirms anon `POST` returns 401 — so this is about the future-proofing claim, not today's surface.)

**Suggested fix**: Add an `alter default privileges` statement that revokes `insert, update, delete` on tables in schema `public` from `anon` and `authenticated` (scoped to the role that owns migrations, e.g. `for role postgres`), keeping the existing revoke for the tables that already exist. If that is deliberately not wanted, correct the comment and the spec bullet so they describe what the statement actually does.

### 🟠 Phone normalization hard-fails on two very common Indian input formats, `supabase/migrations/20260827065400_create_core_schema.sql:101` (with the check at `:91`)

**Problem**: `normalize_buyer_phone` strips non-digits, then prefixes `+91` only when exactly 10 digits remain and a bare `+` otherwise. Two everyday inputs break:

- `09876543210` / `0 98765 43210` (the STD-prefixed form) → 11 digits → `+09876543210` → violates `check (phone ~ '^\+[1-9][0-9]{9,14}$')`.
- `00919876543210` (the international `00` dialing prefix) → `+00919876543210` → same violation.

Both raise a `23514` check violation out of `get_or_create_buyer`, which `getOrCreateBuyerByPhone` (`lib/supabase/queries/buyers.ts:22`) rethrows verbatim.

**Why it matters**: AC-9 says the stored value must be normalized "regardless of what the submitter typed". More concretely: for this product an enquiry submission is the entire conversion event, and a buyer who types their number with a leading `0` gets a failed submission and an opaque Postgres error. That is a lost lead — the one outcome the PRD's user story explicitly cares about. It is also not caught by any test or by `verify.md`, which only exercises the two formats that work.

**Suggested fix**: Before the 10-digit branch, strip a leading `00` (international prefix) and a single leading `0` (STD prefix) from the digit string, then apply the existing `+91`/`+` logic. Add the two failing inputs to `verify.md`'s AC-9 step. If instead the decision is to reject them, the route layer must validate and return a friendly message rather than letting a check-constraint error reach the user — but rejecting a format Indian buyers routinely type seems the wrong trade for this product.

## Minor

### 🟡 `SELECT` is never revoked from anon on the three private tables, `supabase/migrations/20260827065400_create_core_schema.sql:246`

**Problem**: `buyers`, `enquiries`, and `memberships` correctly get no RLS policy, and `verify.md` confirms anon reads return empty. But Supabase's default privileges already granted `SELECT` on them to `anon`/`authenticated`; the only thing stopping reads is "RLS on, zero policies". The migration applies belt-and-braces reasoning to writes (the explicit revoke) but not to reads on the tables holding the most sensitive data.

**Why it matters**: The spec's Security model calls out `buyers.phone`/`email`/`phone_raw`, `enquiries.contact_email`, and `enquiries.message` as personal contact information that must never reach a public read path. With the grant left in place, a single careless future policy (or an `alter table ... disable row level security` during debugging) exposes it. Revoking the grant makes that mistake inert.

**Suggested fix**: Add `revoke select on public.buyers, public.enquiries, public.memberships from anon, authenticated;` alongside the existing revoke. The two views must keep their grants — they are the intended derived-fact surface.

### 🟡 `getCurrentTier` cannot distinguish "not approved yet" from "no membership", `lib/supabase/queries/company-tiers.ts:8`

**Problem**: `company_tiers` filters `where c.status = 'approved'` (migration `:233`). A company that is still `pending`, and a company id that does not exist at all, both return no row, and both fall through to `DEFAULT_TIER` → `"basic"`.

**Why it matters**: A supplier dashboard showing the signed-in supplier's own company (which starts `pending`, per AC-8) would display "Basic" even for a paid Gold membership, with no error to signal that the answer is meaningless. AC-7 is satisfied for the public listing case this helper was written for, but the helper's name and signature promise more than the view can deliver.

**Suggested fix**: Document the approved-only constraint in the JSDoc, and when the supplier dashboard is built (scope feature 10), add a server-only variant that reads `memberships` through `supabaseAdmin` rather than widening the public view to unapproved companies.

### 🟡 `getCurrentTiersFor` has no bound or dedup on the id list, `lib/supabase/queries/company-tiers.ts:20`

**Problem**: `companyIds` goes straight into `.in("company_id", companyIds)`, which PostgREST renders into the query string as `company_id=in.(...)`. Duplicates are passed through, and there is no cap.

**Why it matters**: A listing page with a few hundred companies is fine; a sitemap-style or "all companies" call with a few thousand uuids builds a multi-hundred-kilobyte URL and fails with a 414 or a gateway limit, not a clean error. The helper's whole purpose is the batch case, so it will be reached for by exactly the callers most likely to pass a large array.

**Suggested fix**: Dedup the ids (a `Set`) and chunk the query at a conservative batch size (e.g. 200), merging the results — or document a hard maximum in the JSDoc and let callers paginate.

### 🟡 No automated coverage for the SQL, which is where most of the risk lives

**Problem**: The vitest suite covers the five TypeScript modules well, but nothing automated exercises the RLS policies, the `buyers.phone` normalization trigger, `enquiries_require_reference`, the `memberships_one_active_per_company` partial index, the `ON DELETE SET NULL` / `RESTRICT` behavior, or `get_or_create_buyer`'s conflict clause. `verify.md` records all of these as manually checked once against the live project.

**Why it matters**: These are the security- and correctness-critical branches of the change, and a one-time manual check is not a regression net — a later migration can drop a policy or alter a trigger and nothing will fail. The Major finding above (an unhandled phone format) is precisely the kind of gap an automated SQL test would have surfaced.

**Suggested fix**: Before more features land on this schema, add `supabase test db` (pgTAP) cases for the anon read surface and the three triggers/indexes, mirroring the `verify.md` steps. This is `/test`'s job, not something to fix inline in this change — file it as follow-up.

### 🟡 `assertOwnsCompany` throws an untyped `Error` containing internal identifiers, `lib/auth/assert-company-owner.ts:19`

**Problem**: The failure path throws ``new Error(`Clerk user ${clerkUserId} does not own company ${companyId}`)``. Callers cannot distinguish this from the `throw error` on line 18 (a database failure) without string matching, and the message embeds both ids.

**Why it matters**: This helper is, per the spec's Consequences, the *only* ownership check the project has — "a bug there is a real risk with no second layer catching it". Every mutating route will need to map "not the owner" to a 403 and "database down" to a 500; with both arriving as a bare `Error`, the easy wrong thing (one `catch` → 500, or one `catch` → 403) is what routes will do. Separately, if any route ever echoes `err.message`, it leaks a Clerk user id and confirms a company id's existence to an attacker probing for IDOR.

**Suggested fix**: Export a distinguishable error (a named subclass, or an error carrying a `code`) for the ownership failure, keep the ids out of its message, and log them server-side instead. Doing this now, before any route depends on the current shape, is much cheaper than retrofitting it across every mutating route later.

## Strengths

- The `enquiries_require_reference` `BEFORE INSERT` trigger instead of a table `CHECK` (`20260827065400_create_core_schema.sql:171`) is genuinely subtle and genuinely right: a `CHECK` would re-validate on the `ON DELETE SET NULL` cascades and reject the very deletes AC-5 requires to succeed. The comment explains *why*, not what — exactly the right kind of comment.
- `get_or_create_buyer` as a DB function is the correct call, and the reasoning in its header comment holds up: supabase-js's `.upsert()` really cannot express `do update set email = coalesce(buyers.email, excluded.email)`, and pushing it into one statement is what makes AC-4 atomic. `revoke execute ... from public` + `grant execute ... to service_role` is precisely the right privilege posture.
- `phone_raw := coalesce(new.phone_raw, new.phone)` survives the `ON CONFLICT DO UPDATE` re-fire of the `BEFORE UPDATE` trigger without clobbering the original typed value — an easy thing to get wrong. The normalization is also idempotent under that re-fire (no stored value can have exactly 10 digits, so `+91` is never double-prefixed).
- Migration `20260827065658_harden_function_search_paths.sql` shows the author actually ran `supabase db advisors` and acted on the WARN, rather than shipping and hoping.
- The tests assert real behavior rather than the existence of mocks: error propagation is checked separately from the happy path in every module, `getCurrentTiersFor` verifies the default-then-overlay logic and the no-query-on-empty-input shortcut, and the "secret key, never the publishable key" / "publishable key, never the secret key" assertions in `admin.test.ts`/`client.test.ts` are a real security regression guard on the project's most important boundary.
- `verify.md` is unusually thorough for a data-layer change, with each step mapped to an acceptance criterion.

## Test coverage

**Covered well** (19 tests, 5 files, all passing via `npm test`): both Supabase client constructions including the key-confusion cases; `assertOwnsCompany` across owner / non-owner / DB-error, plus an assertion that *both* `.eq()` filters are applied (which is the actual security property); `getOrCreateBuyerByPhone` argument shaping including the `null`-email → omitted-key path and error propagation; `getCurrentTier` and `getCurrentTiersFor` across hit, miss-defaults-to-basic, empty-input, and error.
